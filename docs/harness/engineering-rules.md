# todopi 工程规则

## 实现

- 先读完所有权文件和现有调用路径再改；不猜 API、不猜依赖行为。
- 把模糊任务转成可验证结果。多种解读会导致不同产物时先澄清；否则显式声明假设。
- 选满足当前需求的最小改动。不顺手清理、不预留配置、不加单一用途的抽象、
  不写掩盖根因的兜底分支。
- TypeScript 严格模式：不用 `any`，不用 `as` 绕过类型，不用 `@ts-ignore`。
  类型报错是设计信号，不是噪音。
- 磁盘读写一律走格式层的单一入口。`.todopi/` 的解析与序列化 MUST 只有一处实现，
  它是 `spec/todopi-format-v1.md` 的唯一执行者。
- 写文件用原子替换（临时文件 + `rename`），不做原地截断写。并发是本产品的正常
  工况：多个 agent、多个分支、多个终端会同时写同一个台账。
- 面向用户的输出（stdout / stderr）是产品表面。改动措辞等同改 UI，先写英文。

## 调试与依赖

- 先复现，再读完整错误与 stack trace；一次只验证一个根因假设。
- 优先用 Node / Bun 标准库和已有依赖。新增依赖必须在 DECISIONS.md 说明理由：
  解决什么问题、为何标准库不够、体积与维护状态。单二进制是产品承诺，
  依赖体积是产品指标。
- 依赖方向、磁盘格式、CLI 接口这类难回退的决策按长期边界设计；
  易回退的实现细节保持简单直接。
- 过时代码路径同批删除，不留兼容层。例外：`.todopi/` 格式的版本兼容，
  那是对用户数据的承诺，按 spec 的版本规则处理。

## 测试

- 格式层（读写 `.todopi/`）必须有基于 spec 条款的测试，测试名指向 spec 章节号。
  spec 的 MUST / MUST NOT 条款没有对应测试，等于没实现。
- CLI 行为测试在真实临时目录里跑，不 mock 文件系统。产品的核心价值就是
  「文件确实躺在仓库里」，mock 掉文件系统等于不测。
- 并发与锁的行为需要并发测试，不能用单线程顺序调用冒充。
- 测试 MUST NOT 访问网络。这既是产品约束也是测试纪律。

## 评审与证据

- 只改需求直接涉及的文件。不顺手格式化、不修无关内容——它们会淹没 diff，
  让评审失去意义。
- 不确定性、阻塞项、没跑的层必须精确说明。MUST NOT 把 `blocked` 写成 `pass`
  或 `not_applicable`。
- 完成前检查 diff，跑完 harness 推导出的全部层，保留结构化结果
  （`.harness-results/`）。
- 代码评审中发现的每一类新错误，提升为 `.harness/arch-rules.json` 里的一条规则。
  评审抓到一次而没有沉淀成规则，就等于把同样的错误留给下一个 session。

## 提交

- 前缀沿用仓库现有风格：`feat:` / `fix:` / `docs:` / `chore:` / `refactor:` / `test:`。
- 一个 commit 一个完整逻辑改动。每次 commit 后仓库都处于一致状态。
- commit message 正文解释 why，不复述 diff 已经说清的 what。
