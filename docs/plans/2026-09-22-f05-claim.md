# F05 `claim` / `release` 实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: 用 superpowers:executing-plans 逐个 task 执行。步骤用 `- [ ]` 便于跟踪。

**Goal:** `todopi claim <id>` 与 `todopi release <id>` 改变任务归属，过期租约的任务可直接重新认领并留痕。

**Architecture:** 派生判断（能不能认领、算不算 steal）落在 `domain/` 的纯函数里；租约的写入端加在 `format/lease.ts`；任务文件的改写走一个从 F03 `createTask` 抽出来的通用 `updateTask`，锁的正确性原样保留。

**Tech Stack:** Node 22 类型剥离直接跑 `.ts`；依赖仍是 `commander` / `yaml` / `fractional-indexing`。

**Spec:** `spec/todopi-format-v1.md` §5.3.3（Log 动词 `claimed` / `released`）、§6.1（状态迁移与门禁）、§6.3（`updated` 必须刷新）、§7.3（stale）、§8（租约与锁）。PRD FR-C1–C6、FR-Q2。

## Global Constraints

- 格式规格是 normative。改 MUST/MUST NOT 要同步 `version` 与迁移说明。
- v0.1 零网络、无遥测、无常驻进程；CLI 不得自动 commit/push/切分支。
- 分层：`commands/` → `output/` → `domain/` → `format/` → `fs/`。`domain/` 不碰 fs；`output/dto/` 从 `domain/` 只能 `import type`（ARCH-020）；`format/` 从 `domain/` 只能引 `types.ts`（ARCH-018）；`fs/` 只 import `node:*`（ARCH-019）。
- 不得用 `enum` / `namespace` / 装饰器（ARCH-013）；不得用显式 `any`（ARCH-015）。
- CLI 的 stdout/stderr 必须是英文；`src/` 里不得有中文字符串字面量（注释可以是中文，ARCH-014）。
- `feature_list.json` 的 `state` / `evidence` 只能由 `make verify-feature` 写。
- 退出码（FR-Q2）：0 ok / 1 usage / 2 gate / 3 conflict / 4 unsupported version。
- 涉及并发的改动必须有多进程用例（ARCH-017）。单进程用例对互斥失效是瞎的——F03 已被证明两次。

## 动手前已核实的三件事

写这份计划时实测过，结论直接影响 Task 划分：

1. **`createTask` 只能建新任务**（`make: (ctx) => NewTask`，写前 `existsSync` 就拒绝），`emitTask` 只接受 `NewTask` 这个定型形状。所以 F05 需要一个通用的「读-改-写」入口，而不是复用 `createTask`。
2. **`emitFrontmatter` 遇到嵌套映射直接抛错**（`external` 就是），注释里写着「保留它们是 F10 edit 的事」。**那个推迟现在不成立了**：`claim` 要改写既有文件，而 `spec/fixtures/valid/unknown-keys.md` 这样的任务带着 `external`——今天 `claim` 它会抛错。F05 必须把这个补上。
3. **`yaml` 包（已是依赖）发射的嵌套映射，我们自己的解析器读得回来**，`external` 的往返实测一致。所以修法是确定的，不需要新依赖。

另外核对过一个假警报：把 valid fixture 重新发射后与原文按 `JSON.stringify` 比较会报「语义变了」，实际只是**字段顺序被规范化**（`blocked_by` 在 `labels` 前），语义一致，而规范化字段顺序正是 §5.1 要求的。写往返用例时要按键集合比较，别按 JSON 字符串比。

## 这个 feature 的核心设计决定：两次写入的顺序

`claim` 要写两个文件——任务文件（committed）和租约文件（运行时，spec §8 明说可随时删除）。两者之间没有跨文件原子性。`withLock` 保证的是**本机同一时刻只有一个写者**，防不住写到一半断电。

两种顺序，各自的残局：

| 顺序 | 崩在中间的残局 | 可恢复性 |
|---|---|---|
| 先租约、后任务文件 | 有租约，任务仍是 `open` | `isStale` 只对 `in_progress` 查心跳，一个挂在 `open` 任务上的租约没人读；`doctor --fix`（F13）清理。重跑 `claim` 即可 |
| 先任务文件、后租约 | 任务是 `in_progress` 但没租约 | `isStale` 回退看 `updated`，等租期过了变 stale 可被重认领。也能恢复，但**提交进仓库的记录跑到了本机事实前面** |

**选先租约、后任务文件。** 理由：committed 的记录永远不领先于真相，而散落的租约文件是规格自己声明为可丢弃的。spec §6.1 的 effects 单元格（`set assignee; create lease`）没有规定顺序，两种都不违规。

顺带一个好处：租约的 `O_EXCL` 创建**本身就是冲突检测**。不需要先读再判再写——`openSync(path, "wx")` 失败就说明有人持有，此时再读它判断是否过期。

### `O_EXCL` 的空文件瞬间

F03 的锁设计一号死在这上面：`openSync("wx")` 之后 `writeSync` 之前，文件是空的。这里这个瞬间是良性的，两个理由都要在实现注释里写清楚：

- `readHeartbeats` 跳过解析不了的 JSON（已有用例），并发的 `ls` 最多短暂看成「没有租约」；
- 写者之间由 `withLock` 排他，不会有第二个写者观察到这个中间态。

所以这里直接 `openSync("wx")` + `writeSync`，不套 `writeFileAtomic`（它是 temp+rename，而 rename 覆盖既有文件恰恰不是 `O_EXCL`，会丢掉冲突检测）。

- [ ] **Step 4: 抽出 `updateTask`**

把 `createTask` 里「取锁 → 读全部 → 造候选 → 校验 → 写」的骨架抽出来，两个入口共用。`updateTask` 的 `mutate` 收到已解析的 `TaskFile` 与本次写入的时间戳，返回**完整的新 frontmatter**：

```typescript
/**
 * 读-改-写一个既有任务。整段在锁内完成，理由与 createTask 相同：
 * 两个并发的写者若各自读到同一份旧内容，后写的会覆盖先写的。
 *
 * mutate 返回完整的新 frontmatter 而不是一个补丁：补丁语义需要定义
 * 「怎么删一个键」，而 undefined 与「键不存在」在 YAML 里不是一回事。
 * 返回全量则不需要这层约定，代价是调用方要把不改的键原样带回来——
 * 那正是 spec §5.2 字段 11 要求的「保留读到的条目」。
 *
 * updated 由这一层统一刷新（spec §6.3：每次写入都要刷新），调用方不管。
 */
export function updateTask(
  ledger: Ledger,
  id: string,
  mutate: (t: TaskFile, now: string) => Record<string, unknown>,
  validate: Validate,
): TaskFile
```

实现要点，逐条都有理由：

- 锁内重新 `readTasks`，**不接受调用方传进来的快照**。调用方在锁外读到的东西，到拿到锁时可能已经变了。
- 找不到 `id` 抛 `CliError(EXIT.usage, ...)`，文案里给出 `todopi ls` 作为下一步。
- `mutate` 返回的 frontmatter 先 `emitTask`/`emitFrontmatter` 再 `parseCandidate` 再 `validate`，顺序与 `createTask` 一致——**校验在写入之前**，这是 F03 第二轮评审的结论（校验在写之后会留下损坏文件）。
- 正文原样带回：只有 frontmatter 被重新发射，body 一个字节都不动，除非调用方显式追加 Log 行。

  | { kind: "reclaim"; replaced: string; stolen: boolean } // in_progress → in_progress

  | { kind: "refuse"; code: 2 | 3; message: string };
